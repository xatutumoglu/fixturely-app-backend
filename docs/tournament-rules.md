# Tournament Rules

This document describes exactly how each supported tournament format is generated, scored, and
resolved. It is the source of truth for behavior that is otherwise only visible by reading the
`Fixturely.Application.Tournaments.Formats` / `.Standings` / `.Bracket` source.

## Supported formats

Fixturely v1 supports exactly four formats (`TournamentFormat` enum):

1. **League**
2. **Group stage** (groups of exactly four)
3. **Single-elimination knockout**
4. **Group stage followed by knockout**

Swiss system, double-elimination, manual bracket mode, public tournaments, and custom
user-defined ranking rules are explicitly out of scope for v1 (see
[assumptions.md](assumptions.md)).

## Tournament lifecycle

`TournamentStatus`: `Draft → Setup → FixtureGenerated → InProgress → Completed → Archived`, with a
separate soft-deleted `Deleted` state.

- **Draft**: settings being finalized on creation; immediately transitioned to **Setup**.
- **Setup**: participants can be added/edited/removed.
- **FixtureGenerated**: a fixture/bracket exists, no match has a completed, non-BYE score yet.
- **InProgress**: at least one real (non-BYE) match has been completed.
- **Completed**: (reserved for future explicit completion workflow) — currently reachable only via
  `Reopen`'s inverse; the domain model supports it but no endpoint currently transitions a
  tournament to Completed automatically. This is a documented simplification (see
  [assumptions.md](assumptions.md)).
- **Archived**: read-only; no mutation endpoint succeeds against an archived tournament.

**Regeneration rule**: `Tournament.CanRegenerateFixture()` returns true only while status is
`Setup` or `FixtureGenerated` **and** no non-BYE match has been completed
(`Tournament.HasAnyScoreEntered()`). Once any real score exists, `POST /regenerate-fixture` is
rejected with `InvalidTournamentStateException` (400).

Every generation and regeneration is recorded in `FixtureGenerationHistory`
(`GenerationNumber`, `TournamentFormat`, `RandomSeed`, `DrawMetadataJson`, `WasConfirmed`,
`SupersededAtUtc`) and mirrored into `AuditLog`. The `RandomSeed` is produced by
`SecureDraw.GenerateSeed()` (`RandomNumberGenerator`-backed) so every random draw is reproducible
and auditable from its stored seed.

## League format

- Requires **at least 2** participants (no upper bound).
- `LegMode.SingleLeg` or `LegMode.DoubleLeg`.
- Fixtures generated by `RoundRobinScheduler` using the standard **circle method**: participants
  are arranged in a circle, one fixed and the rest rotating each round, guaranteeing every pair
  meets exactly once per leg.
- **Odd participant counts**: a `null` "BYE" slot is added to make the count even. Any pairing
  where `Home` or `Away` is `null` is materialized as a `Match` with `IsBye = true`,
  automatically `Completed`, `WinnerParticipantId` set to whichever side is real, and **no score
  entry is possible or required** for BYE matches (`MatchService.UpdateScoreAsync` rejects score
  submission for BYE matches with `InvalidScoreException`).
- **Double-leg**: the second leg's fixtures are the exact mirror (home/away swapped) of the first
  leg, scheduled in the rounds immediately following the first leg's rounds.

### Standings

Standard points: **Win = 3, Draw = 1, Loss = 0**. Standings are **always recomputed dynamically**
from `Completed`, non-BYE matches — never cached as the source of truth (Redis, if used, is only
an invalidate-on-write cache layer).

Each row: `Position, Participant, Played, Won, Drawn, Lost, GoalsFor, GoalsAgainst,
GoalDifference, Points`.

### Ranking / tie-break order

Implemented in `TieBreakerService.OrderByRanking`, applied in this exact order:

1. **Total points** (descending).
2. **Head-to-head points** among the tied subset (mini-table restricted to only the tied
   participants' matches against each other).
3. **Head-to-head goal difference** among the tied subset.
4. **Head-to-head goals scored** among the tied subset.
5. **Overall goal difference** (all matches, not just head-to-head).
6. **Overall goals scored**.
7. **Total wins**.
8. **Controlled tie-break resolution** (see below) — flagged, never silently resolved by
   alphabetic order.

For every criterion, if it produces a further split (e.g. 3 participants tied on points, but only
2 remain tied after head-to-head points), the **remaining tied subset only** is recursively
re-evaluated from the top of the list — this is the "mini-table" behavior: a subset that regains a
tie after being isolated from the rest of the standings is compared again using head-to-head
results **among just that subset**, not the original full-tournament head-to-head, per the
standard "mini-league" convention for 3+ way ties.

If every deterministic criterion is exhausted and participants remain tied (most commonly a
perfectly symmetric 2-team head-to-head draw), `TieBreakerService` marks each such row with a
`TieBreakNote` explaining that a **controlled tie-break resolution** is required:

- **Exactly two tied participants** needing a definitive sporting order (e.g. for a
  championship/qualification place): the documented resolution is a **tie-break match**.
- **Three or more tied participants**: the documented resolution is a **mini-league** among just
  those participants, or an explicitly recorded resolution.
- If domain rules ultimately require a **random draw** as the final tiebreaker, it must use
  `SecureDraw` (cryptographically secure) and be persisted in `TieBreakResolution`
  (`Method = RandomDraw`, `RandomSeed`, `ResolutionDetailsJson`) for full auditability.

**Alphabetic ordering is never used as a sporting tie-breaker** — the only fallback when a
`TieBreakNote` is present is the controlled workflow above; the current API surface reports the
flagged tie via `TieBreakNote` in the standings response and leaves the final resolution as an
Owner-driven action (creating the tie-break match/mini-league is out of scope for the v1 API
endpoints — see [assumptions.md](assumptions.md)).

## Group stage format

- Every group contains **exactly four** participants — `NumberOfGroups × 4` must equal the
  tournament's participant count, or `GenerateFixture` throws
  `TournamentGroupCompositionException` (400).
- Participants are assigned to groups via a **fair random draw**
  (`SecureDraw.Shuffle(participantIds, randomSeed)`, cryptographically seeded, then partitioned
  into consecutive chunks of 4) and recorded in `FixtureGenerationHistory.DrawMetadataJson` and
  `AuditLog`.
- `SingleLeg`: 6 matches per group (all pairs once). `DoubleLeg`: 12 matches per group (home+away).
- Standings and tie-break rules within each group are **identical** to the League rules above,
  scoped to that group's matches only.
- A standalone group-stage tournament (no knockout phase) is complete once each group's own
  standings are final — no further phase is generated.

## Group + knockout format

- Requires `NumberOfGroups ∈ {2, 4, 8, 16}`, each with exactly four participants (so total
  participants ∈ {8, 16, 32, 64}).
- Runs the identical group-stage draw and round-robin described above.
- **Qualification**: the **top two** finishers of every group qualify (by the League/Group
  standings + tie-break rules above).
- **First knockout round pairing**: `GroupKnockoutFormatEngine` creates knockout matches with
  **unresolved qualifier slot references** (`HomeQualifierGroupOrderIndex`/`Position`,
  `AwayQualifierGroupOrderIndex`/`Position`) at generation time — the actual participant ids are
  not yet known. Pairing is computed via a **randomized rotation** of group order indices
  (`SecureDraw.Shuffle` over group indices) such that:
  - The **winner of group *i*** is paired against the **runner-up of a different group** (never
    group *i* itself) — enforced structurally by pairing group *i*'s winner with the next group in
    the shuffled rotation's runner-up, which is provably always a different group index.
  - **No two participants from the same group can meet in round 1**, since a group's winner and
    its own runner-up are never placed in the same first-round match by construction.
  - If a valid pairing cannot be constructed for the given group/participant configuration, a
    `TournamentGroupCompositionException`/`KnockoutPairingException` is raised rather than
    silently producing an invalid bracket.
  - **Once each group's matches all complete**, `QualificationService.TryResolveGroupQualifiersAsync`
    (invoked automatically after every score update in a `GroupKnockout` tournament) computes that
    group's final standings, resolves the winner/runner-up participant ids, and fills in every
    knockout match slot referencing that group's `OrderIndex` via
    `Match.ResolveQualifierSlot`. A knockout match only becomes `Scheduled` (both slots filled)
    once *both* of its referenced groups have finished.
- From the resolved first knockout round onward, bracket construction (later rounds, third-place
  match) follows the same rules as the pure Knockout format below.
- A **third-place match** is included when `HasThirdPlaceMatch = true` on the tournament.

## Knockout format

- `SingleLeg` or `DoubleLeg`.
- Supports **any participant count ≥ 2**, not just powers of two.
- **Bracket construction**: `KnockoutFormatEngine` computes the standard seeding order via
  `BracketSeedOrderCalculator.ComputeSeedOrder` (the well-known recursive seeding pattern that
  keeps seed 1 and seed 2 maximally apart) over the next power-of-two bracket size, then places
  participants into that seed order after a `SecureDraw.Shuffle` (so the actual seed *assignment*
  to participants is randomized, while the seed *pattern* itself remains structurally sound).
- **The full bracket is generated up front** — round 1 through the final (and third-place match)
  — not just the first round; later-round matches simply start with unresolved participant slots
  until their feeding matches are decided.
- **BYE handling**: any seed slot beyond the actual participant count maps to a `null` opponent.
  A first-round match with a `null` opponent is created with `IsBye = true`, is immediately
  `Completed`, and its `WinnerParticipantId` is set to the real participant. `Match.LinkNextMatchSlots`
  means the BYE's "winner" automatically propagates into the next round's slot at generation time
  — **no manual advancement step is required**, and BYE matches never require or accept score
  entry.
- **Winner propagation**: every match stores `NextHomeMatchId`/`NextAwayMatchId` (+ which slot).
  When `MatchService.UpdateScoreAsync` determines a decisive winner, it calls
  `PropagateWinnerAsync`, which assigns that winner into the next match's slot
  (`Match.AssignParticipant`), automatically promoting that next match to `Scheduled` once both
  slots are filled.
- **Third-place match**: generated automatically (as its own `RoundPhase.ThirdPlace` round) with
  `IsThirdPlaceMatch = true` whenever `HasThirdPlaceMatch = true`, fed by the two semifinal
  losers via each semifinal leg's `NextAwayMatchId` link. Its leg mode (single/double) matches the
  tournament's overall `LegMode` unless a future tournament-level override is added.

### Single-leg tie decision (`BracketProgressionService.EvaluateSingleLegTie`)

1. If `HomeRegularTimeScore != AwayRegularTimeScore`, the higher scorer wins — decided.
2. If tied at regular time and no extra-time score has been submitted yet, the match is **not**
   completed and `RequiresExtraTime = true` is signaled.
3. If extra time is tied too and no penalty score has been submitted, `RequiresPenalties = true`.
4. Once penalty scores differ, the higher scorer wins. **A knockout match can never be marked
   `Completed` without a determinable winner** — `Match.CompleteWithWinner` throws
   `InvalidScoreException` if `winnerParticipantId` is `null` for a match with
   `RequiresDecisiveWinner = true` and `IsBye = false`.

### Double-leg tie decision (`BracketProgressionService.EvaluateDoubleLegTie`)

1. **Aggregate score** = leg 1 home goals + leg 2 away goals (for "Team A") vs. leg 1 away goals +
   leg 2 home goals (for "Team B"). Whichever aggregate is higher wins — decided.
2. **The away-goals rule is never applied** — a tied aggregate is *always* resolved by extra time
   and, if necessary, penalties, exactly as if it were a single decisive leg. This is enforced by
   `EvaluateDoubleLegTie` never inspecting which leg was "away" once aggregates are computed.
3. Extra time and penalties, when required, are entered and evaluated **only on the second leg**
   (`leg2.HomeExtraTimeScore`/`AwayExtraTimeScore`/`HomePenaltyScore`/`AwayPenaltyScore`) — the
   first leg's extra-time/penalty fields are never used for a double-leg tie.
4. A participant is **never advanced** before both legs are completed and a winner is known —
   `MatchService.ResolveKnockoutWinnerAsync` returns `null` (no winner yet) whenever the sibling
   leg for a tie hasn't been played, which blocks `PropagateWinnerAsync` from running.

## Score entry, correction, and dependent-match invalidation

- Scores must be non-negative integers (`Match.SetRegularTimeScore` throws `InvalidScoreException`
  otherwise).
- Score updates run inside the same request/transaction as standings-affecting/bracket-affecting
  side effects (winner propagation, qualifier resolution for group+knockout), and every mutation
  is protected by the match's `RowVersion` (stale write → `409 Conflict`).
- **Correcting a historical knockout result**: if the new score changes the winner of a **tie that
  was already completed and had already propagated** to a later round, `MatchService` walks
  forward through `NextHomeMatchId`/`NextAwayMatchId` (`BracketProgressionService.CollectDownstreamMatches`)
  to find every match whose participant slot was populated as a consequence of the now-invalid
  result. By default, the correction request is **rejected with 400** and the list of affected
  downstream match ids, requiring the Owner to resubmit with `confirmDependentInvalidation: true`
  to proceed. When confirmed:
  - Every downstream match's participant slots are cleared and the match is marked `Invalidated`.
  - The original (pre-correction) values are preserved in `AuditLog` before being overwritten.
  - The corrected match itself is then completed with its new winner, and that winner is
    re-propagated forward from scratch.
  - **Fixturely never silently corrupts or preserves logically invalid future results** — a
    downstream match that depended on the old winner is always explicitly invalidated, never left
    referencing a participant who is no longer actually through to that round.

## Timezone handling

All persisted timestamps (`CreatedAtUtc`, `ScheduledAtUtc`, etc.) are stored in **UTC** — this is
structural (`DateTime` fields are always populated from `TimeProvider.GetUtcNow().UtcDateTime`).
The assumed **default display timezone** for any future frontend rendering is **Europe/Istanbul**,
but this is a presentation-layer concern only; the backend never converts or stores local time.
